## 2. 원격 사용: 중간 서버(MCP·FastAPI) 필요 여부

**필요 없다.** CLI가 Ollama HTTP API(`/api/chat`)를 직접 호출한다.

| 방식                           | 구성                                 | 도구가 다루는 파일 | 조건                                                                                                                                                             |
| ------------------------------ | ------------------------------------ | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 서버에 설치, SSH로 사용      | GPU 서버에서 CLI → `127.0.0.1:11434` | GPU 서버           | 지금 패키지 그대로                                                                                                                                               |
| ② 로컬 PC에서 원격 Ollama 사용 | 로컬 CLI → `http://<GPU서버>:11434`  | 로컬 PC            | Ollama `OLLAMA_HOST=0.0.0.0`(127.0.0.1에만 열려 있으면 403), 방화벽 11434 허용. 로컬 PC가 Windows면 Windows용 패키지를 따로 만들어야 함(번들은 같고 Node만 다름) |

- MCP는 CLI에 **도구를 추가**하는 방식(예: 사내 DB 조회 도구)이지 모델 연결
  수단이 아니다.
- 중계 서버가 필요한 경우는 **인증·접근 통제**(Ollama는 인증 기능 없음), 사용
  기록, 사용량 제한, 11434 직접 개방 불가 정책일 때다. 이때도 nginx 리버스
  프록시로 충분하고 CLI는 주소만 바꾼다.

## 3. 웹(브라우저)으로 쓰는 방법

Gemini CLI는 터미널 프로그램이라 웹 채팅 화면이 없다.

| 방법                               | 화면                                        | 작업량                                                                 | 비고                                                                              |
| ---------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| ① 웹 터미널 `ttyd`                 | 브라우저 속 서버 터미널에서 `gemini` 실행   | 코드 수정 없음, 실행 파일 1개 반입                                     | 가장 간단. 로그인 보호(`-c 아이디:비밀번호`) 필수                                 |
| ② 브라우저용 VS Code `code-server` | 브라우저 VS Code의 터미널에서 `gemini` 실행 | 코드 수정 없음, 설치 파일이 ①보다 큼                                   | 파일 편집과 CLI를 한 화면에서. 개발 작업에 적합                                   |
| ③ Ollama 웹 채팅 (예: Open WebUI)  | ChatGPT 같은 채팅                           | 별도 프로그램                                                          | **CLI 에이전트 아님** - 파일·셸·코드 수정 불가                                    |
| ④ 웹 화면 직접 개발                | 자체 채팅 화면                              | 개발 필요. 기반 후보: `packages/a2a-server`(실험 단계), `gemini --acp` | CLI의 "웹 버전"은 이것뿐. Ollama 연동이 `core`에 있어 동작할 것으로 보이나 미확인 |

- 에이전트 기능(파일·셸)을 브라우저에서 쓰려면 ① 또는 ②, 채팅만이면 ③.
- ①·② 공통 주의: 쓰는 사람은 모두 **서버 계정 권한**으로 작업한다 → 로그인 보호,
  사용자별 계정 분리 필요.

## 4. DBAgent(웹)에서 ② code-server 사용

DBAgent-Java 확인 결과: Spring Boot + 정적 HTML·바닐라 JS, 자체 토큰
로그인(`POST /api/login` → `token`을 쿼리·본문으로 전달), **운영은 IBM AIX**.

**전제:** Gemini CLI 패키지와 code-server는 Linux용이라 AIX에서 돌지
않는다(code-server의 AIX 미지원은 일반 지식 기준, 진행 시 확인). code-server는
Linux 서버에 띄우고 DBAgent는 연결만 한다.

| 방법                              | 내용                                                              | 작업량                                                    | 비고                                                                                                                                                          |
| --------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 메뉴 → 새 탭** (권장 시작점) | DBAgent 메뉴 "AI 코딩(Gemini CLI)" → code-server 주소를 새 탭으로 | DBAgent는 메뉴·링크만 추가                                | 가장 안정적. code-server 로그인을 한 번 더 함                                                                                                                 |
| B. DBAgent 화면 안(iframe)        | DBAgent 페이지 안에 code-server                                   | A + nginx로 두 서비스를 같은 주소 아래로                  | 다른 주소를 iframe에 넣으면 로그인 쿠키가 막힐 수 있음. VS Code 웹은 HTTPS가 아니면 일부 기능(클립보드 등)이 제한되는 것으로 알려져 폐쇄망 HTTP에서 확인 필요 |
| C. B + 로그인 통합                | DBAgent 로그인 사용자만 code-server 접근                          | nginx가 DBAgent `/api/check-auth`로 토큰 확인 - 추가 개발 | 로그인 한 번. DBAgent 토큰이 주소 전달 방식이라 쿠키 방식 전환 작업이 따름                                                                                    |

**보안 (결정 필요):** code-server 사용자는 서버 셸을 쓸 수 있다 = DBAgent
사용자에게 서버 셸 권한을 주는 것.

- 권한이 제한된 전용 Linux 계정으로 실행
- 사용 대상을 관리자로 한정할지 결정
- GPU 서버에는 SQL 튜닝 RAG API·Ollama가 있어 **별도 Linux 서버**에
  code-server·CLI를 두고 Ollama만 원격 사용(2절 ②)하는 편이 안전

**DBAgent 쪽 작업은 DBAgent 저장소 규칙(메인·AIX 동기화)에 따라 별도로
진행한다.**

## 4-1. 제약: 폐쇄망 서버는 접근제어 시스템을 거쳐야 함 (SSH 직접 접속 불가)

오케스트레이터 확인(2026-10-01): 폐쇄망 서버는 중간 접근제어 시스템을 거쳐야
하고 SSH를 바로 쓸 수 없다.

참고로 `code-server`는 Coder사의 오픈소스(Code-OSS 기반)로, 마이크로소프트 VS
Code와 달리 확장 스토어가 Open VSX이고 일부 MS 전용 확장(Copilot, Pylance, 원격
개발 등)은 쓸 수 없다. 비슷한 공식 기능으로 VS Code의 `code serve-web`이
있다(라이선스 확인 필요). 둘 다 폐쇄망에서는 확장을 `.vsix`로 반입한다(일반 지식
기준, 진행 시 확인).

| 방식                                          | 접근제어 환경에서                                                                                                                       | 판단                            |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| VS Code Remote-SSH                            | 직접 SSH·서버 쪽 구성요소 설치·포트 포워딩이 필요해 막힐 가능성이 큼                                                                    | 제외                            |
| code-server·ttyd (웹 셸)                      | 기술적으로는 가능하나 **접근제어·감사 기록을 우회하는 셸 경로**가 됨                                                                    | 보안 부서 승인 없이는 불가로 봄 |
| 접근제어 터미널로 접속 → 서버에서 `gemini`    | 접근제어가 주는 터미널이 일반 터미널이면 사용 가능. 웹 터미널이면 대화형 화면이 깨질 수 있음(시험 필요). `gemini -p`는 무난할 것으로 봄 | 서버 쪽 작업용 보조 수단        |
| **사용자 PC에서 CLI + GPU 서버 Ollama(HTTP)** | SSH 불필요. Ollama HTTP 연결만 필요하고 서버 셸을 열지 않아 접근제어를 우회하지 않음. 도구는 사용자 PC 파일을 다룸                      | **1순위로 변경**                |

1순위 방식의 전제:

1. 사용자 PC에서 GPU 서버 HTTP 포트(11434 또는 nginx 포트)로 가는 길(방화벽).
   DBAgent의 AI DBA·SQL 튜닝 API가 이미 HTTP로 붙는 것과 같은 종류.
2. Ollama는 인증이 없으므로 nginx 앞단 인증 또는 출발지 IP 제한.
3. 사용자 PC가 Windows면 Windows용 패키지 추가 제작(번들은 같고 Node 런타임만
   다름).

**code-server와 지금 REST API의 차이 (2026-10-01 질의):** 둘 다 "포트를 열고
방화벽을 허용"하는 배포 방식은 같다. 차이는 포트로 내주는 것 - REST
API(`SqltuneRestApi`, Spring Boot, Ollama는 `localhost:11434`로 내부 호출)는
**정해진 기능**만, code-server는 **서버 계정 셸·파일 전체**(브라우저로 하는
SSH)를 내준다. 방화벽 신청 형태가 같아도 접근제어 우회로 볼 수 있으므로 쓰려면
"브라우저 원격 개발 환경"으로 명시해 승인받는다.

**선택지 추가 - 기존 REST API를 Ollama 입구로 사용:**

```
사용자 PC [gemini CLI] --HTTP(이미 열린 REST API 포트)--> REST API [/ollama/api/chat 중계] --localhost--> Ollama
```

- 새 방화벽 포트 불필요, Ollama(11434)는 계속 비노출, REST API에서 인증 가능
- CLI 수정 없음: `GEMINI_OLLAMA_BASE_URL=http://<GPU서버>:<REST포트>/ollama` →
  `/ollama/api/chat`으로 요청(주소 뒤에 `/api/chat`을 붙이는 구현)
- REST API 작업: NDJSON 스트리밍을 **조각 단위로 그대로 흘려보내는** 중계
  엔드포인트 추가(모아서 보내면 CLI 타임아웃·스트리밍 표시 불가)
- SQL 튜닝 API와 같은 Ollama를 나눠 씀 - `num_ctx` 32768로 같아 재적재는 없지만
  동시 사용 시 대기

다음에 확인할 것:

0. 기존 REST API를 Ollama 입구로 쓸지, 쓴다면 인증 방식
1. 사용자 PC 운영체제 (Windows / Linux)
2. 사용자 PC → GPU 서버 HTTP 포트 접근 가능 여부 (DBAgent·SQL 튜닝 API와 같은
   경로인지)
3. 접근제어 시스템의 터미널 종류(전용 클라이언트 / 웹 터미널), 포트 포워딩·파일
   전송 허용 여부
4. 보안 정책: 웹 셸(code-server 등) 허용 가능성, 내부 HTTP 서비스 노출 규정
